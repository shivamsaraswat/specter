# Feature Specification: Rule Engine

**Feature Branch**: not yet created (spec directory `phase-2/milestone-3-rule-engine`)

**Created**: 2026-10-08

**Status**: Draft

**Input**: User description: "let's take milestone 3 of phase 2". This covers Phase 2 / Milestone 3
of `plan.md`, the rule engine. A "Generate threats" action runs the threat library (Milestone 2)
against a threat model's diagram (Milestone 1) and creates the threats it proposes, marked as
rule-generated, each with its suggested mitigations. Running it again is safe: it never creates a
second copy of a threat it already created, never overwrites what the user has changed, and flags
the threats whose triggering element, property or rule no longer holds as stale instead of deleting
them. Filtering threats by element and showing threat counts on the canvas are Milestone 4.

## Clarifications

### Session 2026-10-08

- Q: Deleting an element that has linked threats is refused today (Milestone 1, scenario 3).
  After generation almost every element has threats. Should deletion keep refusing, or keep and
  unlink the threats (flagging generated ones stale)? → A: Keep refusing, unchanged from
  Milestone 1. A threat's element therefore always exists, and "element deleted" is not a stale
  reason (US3 scenario 5, FR-013).
- Q: When a generated threat goes stale because its rule no longer applies, should the reason say
  which condition stopped holding? → A: Yes. It names each of the rule's conditions that no longer
  holds (flag with its required and current value, element type, boundary crossing, endpoint type),
  worked out at run time from the rule and the current diagram; no snapshot is stored (FR-011).
- Q: If a user deletes a generated threat and its rule still applies, should the next run create it
  again? → A: Yes. Deletions are not remembered; the delete confirmation for a generated threat says
  it will come back and points to "not applicable" as the way to dismiss it (US2 scenario 6,
  FR-016a).
- Q: For the largest diagram (1,000 elements), what is the longest a run may take? → A: Under 30
  seconds, a margin under common 60-second proxy timeouts. If the connection drops, the user is told
  the outcome is unknown and that retrying is safe, since a re-run never duplicates (SC-007, US1
  scenario 9, FR-004).
- Q: What should generation do with an element whose stored properties include keys outside the
  flag vocabulary (possible for elements written before Milestone 1, which keeps them readable)? →
  A: Skip it: no candidates for it, and its existing generated threats are left exactly as they are
  (neither matched nor flagged stale). The run succeeds for every other element and reports which
  elements were skipped; changing any property of such an element in the editor cleans it up
  (Milestone 1), and the next run includes it (FR-002a). Decided while remediating
  `/speckit-analyze` finding C1.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Generate threats from the diagram (Priority: P1)

A security engineer has drawn a diagram and set some security flags. They choose "Generate threats"
on the threat model page. Specter creates one threat for every rule that applies to every element
of the diagram, each linked to its element, marked as rule-generated, carrying the rule's
identifier, and with the rule's suggested mitigations attached as proposed mitigations. The engineer
then sees a short summary of what happened and the new threats in the threat list.

**Why this priority**: This is the milestone. It turns the diagram from documentation into a threat
model, and it is the "generate STRIDE threats" step of Phase 2's Definition of Done.

**Independent Test**: In a new threat model, draw an external entity, a process and a data store
inside a trust boundary, connect them with two data flows (one crossing the boundary), leave every
flag "not assessed", and choose "Generate threats". Check that the threat list now holds exactly
the threats the library returns for those five elements, each linked to its element, marked as
rule-generated, with its mitigations, and that the summary reports the same number as created.

**Acceptance Scenarios**:

1. **Given** a diagram with no rule-generated threats, **When** the user generates threats, **Then**
   one threat is created for each pair of element and applicable rule, and no other threat is
   created.
2. **Given** a generated threat, **When** the user opens it, **Then** its category, title,
   description, likelihood and impact are the rule's (with the element's name filled in), its
   status is open, it is linked to its element, it shows that it was generated by a rule and which
   rule, and its mitigations are the rule's suggested mitigations, each with status proposed.
3. **Given** a data flow from a node outside a trust boundary to a node inside it, **When** threats
   are generated, **Then** the flow receives the threats of rules that require crossing a trust
   boundary, and a flow between two nodes inside the same boundary does not.
4. **Given** a diagram containing only trust boundaries, or no elements at all, **When** the user
   generates threats, **Then** nothing is created and the summary says so.
5. **Given** threats the user created by hand, **When** threats are generated, **Then** those
   threats are left exactly as they were.
6. **Given** diagram changes that are still being saved, **When** the user generates threats,
   **Then** generation waits until those changes are saved, so it runs against what the user sees.
7. **Given** generation succeeds, **When** it finishes, **Then** the user sees how many threats were
   created, how many already existed, how many were newly flagged stale and how many are no longer
   stale, and the names of any elements that were skipped (FR-002a).
8. **Given** generation fails on the server part-way, **When** the user looks at the threat list,
   **Then** nothing from that run was saved, and the user is told it failed and can try again.
9. **Given** the connection drops before the result arrives, **When** the user is told, **Then** the
   message says the run may or may not have completed and that running it again is safe; running it
   again gives the same threats as if the first run had never happened or had completed.
10. **Given** an element whose stored properties include keys outside the flag vocabulary, **When**
    threats are generated, **Then** every other element gets its threats, that element gets none and
    its existing threats are untouched, and the summary names it and says how to clean it up.

### User Story 2 - Re-run safely after changing the diagram (Priority: P1)

The engineer keeps refining the diagram after the first run: adds elements, sets flags, moves nodes
into boundaries. They generate threats again. Specter adds only the threats that are new, leaves
every existing threat as the user left it, and creates no duplicates however often it is run.

**Why this priority**: Diagrams are drawn iteratively. If a re-run duplicated threats or undid the
user's edits, users would generate once and never again, and the threat model would drift from the
diagram. `plan.md` names idempotency as part of this milestone.

**Independent Test**: Generate threats, then edit one generated threat's title, likelihood and
status, delete one of its mitigations, add a new process to the diagram, and generate again. Check
that only the new process's threats were created, that the edited threat kept every change, and
that the total count is what a single run against the final diagram would give.

**Acceptance Scenarios**:

1. **Given** threats were generated and nothing changed since, **When** the user generates again,
   **Then** no threat is created, changed or flagged, and the summary reports everything as
   already existing.
2. **Given** an element added after the last run, **When** the user generates again, **Then** only
   that element's threats are created.
3. **Given** a generated threat the user has edited (title, description, likelihood, impact,
   status) or whose mitigations they changed, added or deleted, **When** the user generates again,
   **Then** none of those changes is undone and no mitigation is re-added.
4. **Given** an element whose flag changed so that a new rule applies (for example
   `internet_facing` set to yes on a process), **When** the user generates again, **Then** that
   rule's threat is created for the element, and the element's other threats are untouched.
5. **Given** the user double-clicks "Generate threats", or two people generate on the same threat
   model at the same moment, **When** both runs finish, **Then** each threat exists once.
6. **Given** a generated threat the user deleted, **When** the user generates again and its rule
   still applies, **Then** the threat is created again (see Assumptions: "not applicable" is how a
   threat is dismissed for good).

### User Story 3 - See which generated threats no longer fit the diagram (Priority: P1)

When the diagram changes so that a generated threat's reason no longer holds (a flag was turned
on, the element changed type, a flow no longer crosses a boundary, or the rule was retired from the
library), the next run flags the threat as stale and says why. The
threat is not deleted: it may carry mitigations, status and notes the user wants to keep, and a
security tool should never make a threat disappear on its own. The user decides what to do with it.

**Why this priority**: Without this, a re-run either leaves outdated threats looking current or
deletes the user's work. `plan.md` requires stale threats to be "flagged as stale instead of
silently deleted".

**Independent Test**: Generate threats for a data flow with `encrypted_in_transit` not assessed,
then set `encrypted_in_transit` to yes and generate again. Check that the unencrypted-flow threat is
still there, marked stale with a reason naming the change, and that its status and mitigations are
unchanged. Set the flag back to "not assessed", generate again, and check that the same threat is
no longer stale and no second copy was created.

**Acceptance Scenarios**:

1. **Given** a generated threat whose rule no longer applies to its element because a flag, the
   element's type or (for a data flow) its boundary crossing or endpoint types changed, **When** the
   user generates again, **Then** the threat is flagged stale with a reason that names each of the
   rule's conditions that no longer holds (for example "requires Encrypted in transit to be No; it
   is Yes"), and nothing else about it changes.
2. **Given** a stale threat whose rule applies again, **When** the user generates again, **Then**
   the stale flag is cleared and no duplicate is created.
3. **Given** a generated threat whose rule was retired from the library, **When** the user
   generates again, **Then** the threat is flagged stale with the reason "rule retired", the
   retirement reason, and the replacement rules, if any; and any replacement rule that applies to
   the element creates its own threat.
4. **Given** two rules that are versions of one threat (a variant group, Milestone 2) and an element
   change that makes the other version apply, **When** the user generates again, **Then** the old
   version's threat is flagged stale and the new version's threat is created.
5. **Given** an element with generated threats (or a node whose flows have them), **When** the user
   tries to delete it, **Then** the delete is refused exactly as Milestone 1 refuses it for any
   linked threat, and the user is shown the linked threats, so they can delete those threats first.
   No threat is changed.
6. **Given** a stale threat, **When** the user changes its status, edits it, or deletes it, **Then**
   that works as for any other threat; the stale flag is never set or cleared by the user directly.
7. **Given** a threat list containing stale threats, **When** the user looks at it, **Then** each
   stale threat is visibly marked and its reason can be read without opening another page.

### User Story 4 - Tell generated threats apart from manual ones (Priority: P2)

In the threat list, the engineer can see which threats were written by hand and which were
generated by a rule, and for a generated threat, which rule produced it. Rule-generated provenance
can't be faked or rewritten by anyone.

**Why this priority**: Specter's "one data model" principle depends on origin being visible and
trustworthy; a reviewer approving a threat model needs to know which threats a person wrote and
which came from defaults. It is P2 because generation works without it, but reviews don't.

**Independent Test**: Generate threats in a model that also has manual threats. Check each row
shows its origin, and that generated rows show the rule identifier. Then try, through the API, to
create a threat marked as rule-generated, and to change a generated threat's rule identifier or
element; check that each is refused.

**Acceptance Scenarios**:

1. **Given** a threat list with manual and generated threats, **When** the user reads it, **Then**
   each threat shows whether it is manual or rule-generated, and each generated threat shows its
   rule identifier.
2. **Given** an API client, **When** it tries to create a threat marked as rule-generated, **Then**
   the request is refused, as it already is today.
3. **Given** a rule-generated threat, **When** an API client tries to change its rule identifier or
   move it to a different element, **Then** the request is refused and nothing changes.
4. **Given** a manual threat that carries a library reference (the API allows one today), **When**
   threats are generated, **Then** it is never matched, changed or flagged stale.

---

### Edge Cases

- **Element renamed after generation.** The threat keeps the title it was created with; a re-run does
  not rewrite it, because the user may have edited it. The user can edit the title. (A future rule
  wording change in the library is treated the same way.)
- **Node type changed** (allowed with threats linked, Milestone 1). The old type's generated threats
  go stale ("the rule no longer applies"); the new type's threats are created.
- **Node moved into or out of a trust boundary.** Its flows' boundary crossing may change, so flow
  threats may go stale or be created, although no flag changed (Milestone 2's edge case).
- **Nested boundaries.** Boundary crossing follows Milestone 2's definition: a flow crosses a trust
  boundary when its two ends are not inside exactly the same set of boundaries.
- **Element with no position yet.** Elements created through the API without a position are still
  part of the diagram and get threats; position plays no part in generation.
- **Deleting an element after generation.** Refused while it, or any flow deleted with it, has
  threats (Milestone 1, unchanged). The user deletes those threats first, then the element. If they
  delete the threats but keep the element, the next run creates them again (see Assumptions).
- **A rule identifier the library doesn't know at all** (neither active nor retired) on a generated
  threat is flagged stale with the reason "rule not in the library". The library's identifier registry
  makes this unlikely, but the engine must not fail on it.
- **A generated threat dismissed as "not applicable"** stays dismissed: a re-run never changes a
  status, and does not recreate it because it still exists.
- **Threat model status.** Generation works whatever the threat model's status (draft, in review,
  approved); status is a label and locks nothing today.
- **Element with properties outside the vocabulary.** Elements written through the API before
  Milestone 1 may hold keys the vocabulary doesn't know. They are skipped and named in the result
  (FR-002a); one such element never blocks the rest of the diagram. Their generated threats, if any,
  are left as they are until a run can evaluate the element again.
- **The library fails to load.** Generation reports an error and changes nothing; it never runs with
  part of the library (Milestone 2, FR-013).
- **Very large diagrams.** The largest diagram (1,000 elements) can produce more than 10,000 threats
  with several mitigations each. Generation must complete or fail as a whole; it must not leave a
  partial result.
- **Diagram edited during a run.** A run works from one consistent view of the diagram. Changes saved
  while it runs are picked up by the next run.

## Requirements *(mandatory)*

### Functional Requirements

**Generating**

- **FR-001**: Users MUST be able to generate threats for a threat model from the threat model page
  in the web app. The same action MUST be available to API clients and documented with the rest of
  the API.
- **FR-002**: Generation MUST ask the shipped threat library (Milestone 2) for the candidate threats
  of every element of the threat model except trust boundaries, supplying for each data flow its
  context: whether it crosses a trust boundary (Milestone 2, FR-010b, computed from the boundaries
  that enclose each end), the types of its source and target, and their names.
- **FR-002a**: An element whose stored properties don't fit the property vocabulary for its type
  MUST be skipped: it gets no candidates, and its existing generated threats MUST NOT be matched,
  changed or flagged stale by that run. The run MUST still succeed for every other element and MUST
  report which elements were skipped, so the user can fix them (changing any of their properties in
  the editor removes the unknown keys, Milestone 1).
- **FR-003**: For every candidate with no matching generated threat (FR-006), generation MUST create a
  threat linked to the element, with the candidate's category, title, description, likelihood and
  impact, status open, origin "rule", and the rule identifier as its library reference; and one
  mitigation per suggested mitigation, with status proposed and no ticket link.
- **FR-004**: Generation MUST be all-or-nothing: if any part of a run fails, nothing from that run is
  saved and the user is told it failed. When the user can't know the outcome (the connection dropped
  before the result arrived), the web app MUST say so and that running it again is safe (FR-008).
- **FR-005**: A run MUST work from one consistent view of the diagram and its threats, and runs on
  the same threat model MUST NOT interleave, so that two runs started at the same time cannot both
  create the same threat.

**Matching and idempotency**

- **FR-006**: A generated threat MUST match a candidate when it has origin "rule", is linked to the
  candidate's element, and its library reference equals the candidate's rule identifier. Nothing else
  (title, category, text) is used for matching. Threats with any other origin MUST never be matched,
  changed or flagged by generation.
- **FR-007**: For a candidate that already has a matching threat, generation MUST NOT create anything
  and MUST NOT change that threat's title, description, category, likelihood, impact, status or
  mitigations, whatever the user did to them.
- **FR-008**: Running generation twice on an unchanged diagram MUST leave the threat model exactly as
  the first run left it.
- **FR-009**: A generated threat's library reference and element link MUST NOT be changeable by any
  client, and no client may create a threat with origin "rule"; only generation writes them. (Origin
  is already unchangeable and a client can already only create manual threats.)

**Stale threats**

- **FR-010**: Each threat MUST carry a stale marker, off by default, which only generation can turn
  on or off. While it is on, the threat MUST also carry the
  reason it is stale, readable by users and API clients.
- **FR-011**: On each run, every generated threat that matches no candidate MUST be flagged stale,
  with one of these reasons:
  - **the rule no longer applies to this element**, naming every one of the rule's conditions that
    no longer holds: a flag, with the value the rule requires and the element's current value ("not
    assessed" shown as such); the element's type, when it is no longer the rule's type; and for a
    data flow, its boundary crossing or endpoint type, with the required and current value. This is
    worked out at each run from the rule's conditions and the current diagram, so nothing about the
    element's earlier state is stored. It names flags and types only, never element names or other
    user text;
  - **rule retired**, together with the library's retirement reason and replacement rules;
  - **rule not in the library**.
- **FR-012**: On each run, every stale generated threat that matches a candidate again MUST have its
  stale flag and reason cleared. A threat that stays stale MUST have its reason replaced with the
  current one, so the reason always describes the diagram as of the latest run.
- **FR-013**: Deleting an element that has linked threats, generated or manual, MUST stay refused as
  in Milestone 1, in the editor and the API alike. This milestone MUST NOT change that behaviour.
- **FR-014**: Generation MUST NOT delete any threat or mitigation, ever.

**Seeing the result**

- **FR-015**: After a run, the user MUST see how many threats were created, how many already existed,
  how many were newly flagged stale and how many stopped being stale, and which elements were
  skipped (FR-002a), if any. Threats that stopped being stale are among those that already existed:
  the two counts overlap, and the summary says so. API clients MUST receive the same information.
- **FR-016**: The threat list MUST show, for every threat, whether it is manual or rule-generated
  (and the rule identifier for a generated one), and for every stale threat a visible marker and its
  reason.
- **FR-016a**: When the user is about to delete a generated threat, the confirmation MUST say that
  the next run will create it again while its rule still applies, and that setting its status to
  "not applicable" dismisses it for good. Deleting a generated threat MUST NOT be recorded anywhere
  for generation to consult.
- **FR-017**: While generation is running, the user MUST see that it is in progress and MUST NOT be
  able to start a second run from the same page.

**Logging and limits**

- **FR-018**: Each run MUST write one log line in the existing write-log style: who ran it, on which
  threat model, the four counts of FR-015 and the number of skipped elements, never threat text or
  element names. Threats and
  mitigations created by a run are not logged one line each.
- **FR-019**: Generation MUST handle the largest diagram a threat model can hold (1,000 elements),
  whatever number of threats that produces, without a partial result (FR-004).

**Scope guard**

- **FR-020**: This milestone MUST NOT add filtering of the threat list by element, threat counts on
  the canvas, a risk summary, or changes to the threat status lifecycle; those are Milestone 4. It
  MUST NOT change which rules exist or how the library decides what applies; that is Milestone 2's
  library and is changed by editing its rule files.

### Key Entities *(include if feature involves data)*

- **Generation run**: one execution of "Generate threats" on one threat model. Not stored; it
  produces threats, stale-flag changes, a summary (four counts and the skipped elements) and one log
  line.
- **Generated threat** (existing threat, origin "rule"): a threat created by a run. Its element link
  and library reference identify which element and rule it came from and never change; everything
  else is the user's to edit.
- **Stale marker** (new, on a threat): whether a generated threat's reason no longer holds, and why:
  rule no longer applies (with each condition that fails now), rule retired (with the library's reason and replacements), or rule not in
  the library. Set and cleared only by generation.
- **Suggested mitigation → mitigation** (existing): each of a rule's suggested mitigations becomes a
  mitigation of the generated threat, status proposed, owned by the user from then on.
- **Flow context** (Milestone 2): boundary crossing and endpoint types of a data flow, worked out from
  the stored diagram by this milestone and handed to the library.
- **Threat library** (Milestone 2): the shipped catalog of rules, asked for candidates and for the
  status of a rule identifier (active, retired, unknown).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For any diagram, the generated threats after one run are exactly the candidates the
  library returns for its elements (those not skipped under FR-002a): no missing threat, no extra
  threat.
- **SC-002**: Running generation any number of times on an unchanged diagram creates zero additional
  threats or mitigations and changes zero existing records after the first run.
- **SC-003**: Every user edit to a generated threat or its mitigations survives every later run: 0%
  of edits lost.
- **SC-004**: Every generated threat whose rule no longer applies to its element, or whose rule was
  retired, is flagged stale with the right reason after the next run; 0% are deleted.
- **SC-005**: Two runs started at the same moment on the same threat model result in each threat
  existing exactly once.
- **SC-006**: Generating threats for a typical diagram of 50 elements takes under 5 seconds from
  clicking the action to seeing the summary.
- **SC-007**: Generating threats for the largest possible diagram (1,000 elements, about 15,000
  threats) completes in under 30 seconds, or fails leaving nothing behind.
- **SC-008**: A user who has drawn a diagram can generate threats, and tell a generated threat from a
  manual one and a stale one from a current one in the threat list, without instructions, on the
  first try.
- **SC-009**: In the app as it is shipped and started (`docker compose up`), drawing a diagram and
  generating threats works end to end, and the browser tests cover it, as Phase 2's Definition of
  Done requires.

## Assumptions

- **"Triggering element no longer exists."** `plan.md` lists this as a stale case, but an element with
  threats can't be deleted (Clarifications), so a generated threat's element always exists. The
  element-related stale cases are the ones that remain possible: its type, flags or flow context
  changed so the rule no longer applies.
- **Re-generating a deleted threat.** A generated threat the user deletes is created again by the next
  run if its rule still applies; no record of the deletion is kept (Clarifications, FR-016a). Setting
  a threat's status to "not applicable" (already possible in the threat table) is how a user dismisses
  a generated threat for good, and it leaves a visible, reviewable record of that decision.
- **No overwriting, ever.** Re-runs never refresh a generated threat's text, even when the element was
  renamed or the rule's wording improved. Keeping the user's edits safe matters more than keeping
  default text current; a stale flag only reports reasons that no longer hold, not wording drift.
- **Stale is not a status.** The stale marker sits alongside the threat's status (open, mitigated,
  accepted, not applicable), which Milestone 4's lifecycle owns. A stale threat keeps its status.
- **Who can generate.** Any signed-in user, like every other write in `/api/v1` today; the app still
  has a single trust tier until Phase 6.
- **Where the action lives.** On the threat model page, so it is reachable from both the Diagram and
  the Threats tab; the summary and the new threats appear in the Threats tab. Exact placement is a
  design decision for planning.
- **Element column.** The threat table already shows each threat's element by name, so generated
  threats are already associated with their element in the list. Filtering by element is Milestone 4.
- **No cap on threats.** No limit on threats per threat model is added. The element limit (1,000) and
  the library's size bound what one run can create (about 15 threats and 50 mitigations for the
  most-flagged process today, so roughly 15,000 threats for a maximum diagram). The constitution's
  Denial of Service note is updated with this bound.
- **Constitution update.** Generation is a new entry point and the first server-side writer of
  origin "rule" (the constitution says none exist before Phase 2). Principle V requires the Threat
  Model section to be updated in the change that implements it, including the bound on what one run
  can write and the new protection of a generated threat's library reference and element link.
- **The library ships with the app.** The rule files are part of the app as installed, so generation
  needs no configuration, network access or file outside the app (constitution Principle IV).
- **Synchronous, not a background job.** A run happens within the user's request and they wait for
  the summary. Background jobs arrive with the worker in Phase 3; the targets in SC-006 and SC-007
  fit inside a request.
- **Library reference on manual threats.** The API lets a manual threat carry a library reference
  today. That stays allowed, and such threats are ignored by generation (FR-006).
